# 核心业务流程

## 1. 登录和会话

```text
pages/login/index
→ pages/login/password
→ POST /api/login {username,password}
→ Shiro Subject.login
→ 返回 Session ID 作为 token
→ 本地 storage 保存 token
→ reLaunch pages/index/index
→ 后续请求携带 Authorization: Bearer <token>
```

后端 Session 默认空闲 30 分钟。无 refresh token。退出时调用 `/api/logout`，随后删除本地 Token。

注意：当前真实 HTTP 401 不会被前端正确处理；原生重构前应先修复统一请求层。

## 2. 公司上下文

公司是多数现场业务的上层上下文：

```text
GET /api/fire/company/myList
→ 用户选择 companyId
→ POST /api/fire/company/switch
→ 后端保存 currentCompanyId 到 Shiro Session
→ GET /api/fire/company/current
→ 各页面携带或读取 companyId
```

后端部分接口还会从 Session 中读取 `currentCompanyId`，但建筑、设备、巡检等接口也接受客户端 `companyId`。应在后端统一验证当前用户是否能访问该公司。

### 建筑编码

管理端「建筑信息」与「客户编辑-建筑」入口已统一：

- 新增：后端自动分配 `B` + ≥4 位数字，表单不再手填编码。
- 编辑：编码只读展示，服务层强制保留库中原值。
- 小程序 `POST /api/fire/building/add|edit` 同样不信任客户端 `buildingCode`。

## 3. 维保任务

### 页面链路

```text
首页
→ task/index：我的任务
→ task/action：常规维保 / 消防设施测试
→ task/detail：一级系统列表
→ task/system：二级设备列表
→ task/device：三级检查项
→ 更新检查结果、故障描述、图片和其他说明
```

### API 链路

```text
GET  /api/fire/company/current
POST /api/fire/task/myList
GET  /api/fire/task/detail/{taskId}
GET  /api/fire/task/system/{recordId}
GET  /api/fire/task/equipment/{recordId}
POST /api/fire/task/updateCheckResult
POST /api/fire/task/updateFaultDesc
POST /api/fire/task/updateCheckDetail
```

关键标识：

- `companyId`：客户/项目范围。
- `taskId`：维保任务。
- `recordId`：系统、设备或检查项记录。
- `recordType`：`0` 常规维保，`1` 消防设施测试。

### 完成规则

小程序当前没有整单“提交完成”动作。后端在任务列表查询中统计所有 `level=3` 的检查项：只要全部 `check_result != 0`，列表状态即表现为完成。

### 当前断点

二级设备的维护/测试弹窗提交到 `/api/fire/task/updateMaintenance`，后端没有该 REST 路径。管理端同名接口不能直接替代。

### 管理端任务弹窗

维保任务列表（`fire/task/task.html`）打开「维保维护 / 消防设施测试」时，弹层目标约 `1350×900`（相对原 `900×600` 放大约 50%），并按视口收缩为 `min(1350, vw×0.94) × min(900, vh×0.92)`。签到、简报等其它弹窗尺寸不变。

### 管理端列表三卡片布局

维保任务页自上而下为三张独立卡片（不要把分类塞进搜索表单）：

1. **搜索卡片**（`search-collapse`）：所属客户、任务名称、任务状态、周期类型、年份、搜索/重置；隐藏域 `taskType`、`params[dashboardFilter]`。
2. **任务分类卡片**（`task-type-card`）：全部任务 / 周期任务 / 临时任务；`searchByType` 写入 `#taskType` 后查询，与搜索条件组合；默认「全部任务」。
3. **列表卡片**（工具栏 + `select-table`）：新增/删除/导出及表格。

首页统计卡片可通过 `params[dashboardFilter]`（白名单：`pending`/`doing`/`today`/`completed`/`overdue`/`mine`）进入任务列表并与上述分类组合；实现见 `fire_main.html`、`task.html` 与 Mapper 动态条件。

### 消防首页全局统计卡跳转

管理员全局首页四张数字卡（`fire_main.html` / `#globalStatsBlock`）整卡可点，走现有 `openMenu` 页签（不 `window.location`）：

| 卡片 | 目标菜单 URL | 说明 |
|---|---|---|
| 公司总数 | `/fire/company` | 公司信息列表 |
| 建筑总数 | `/fire/building` | 建筑信息 |
| 设备总数 | `/fire/equipment` | 设备信息（清除到期快捷筛选） |
| 即将过期 | `/fire/equipment` | `params[expireFilter]=expiringSoon` |

「即将过期」规则与 `FireEquipmentMapper.countExpiringSoon` 一致：`expire_date` 非空且落在 `[CURDATE(), CURDATE()+30天]`。设备列表通过 `sessionStorage` + `postMessage`（`fire-equipment-expire-filter`）刷新已开页签。侧栏无对应菜单时提示「暂无访问权限」。下方快捷入口逻辑不变。

### 管理端搜索栏布局（页面级）

字号偏大导致标签被公共 `.select-list label{width:65px}` 拆行时，**不要**回退全局 body/ry-ui 字体来「修布局」。应在页面搜索区加专用 class：

- 维保签到 / 维保任务 / 故障报修 / 维保报告：`fire-search-layout`（缩小间距、标签 `width:auto` + `nowrap`、控件略收窄；整组可换行）
- 项目类别：`system-type-search`（仅该页）

禁止给全局 `.select-list` / `.form-group` / `.control-label` 加 flex、固定宽或 nowrap。任务分类卡、工单分类卡仍独立于搜索表单。

### 检查项状态与其他说明

三级检查页（维护 `equipment.html`、消防测试 `fire_test_equipment.html`；小程序 `pages/task/device`）：

- **设备状态**只通过外层「正常 / 故障 / 无此设备」写入 `check_result`（`1`/`2`/`3`），接口 `updateCheckResult`。
- **其他说明**按钮打开弹窗，仅编辑 `other_notes` 与 `fault_images`（附件仍挂在同一 `recordId`）；标题为「其他说明」，不再含「是否完好 / 设备状态」。
- 保存说明/附件调用 `updateCheckDetail` 时**不传** `checkResult`，后端动态 SQL 不覆盖已选状态；空串可清空说明或附件。
- 小程序布局：名称/编码 → 三状态按钮 →「其他说明」入口；弹窗同样只含说明与附件。

### 维保签到数据权限

签到功能保留（菜单/页面/接口/表/历史数据均不删除）。管理端与小程序列表/详情/导出统一走 `IFireDataPermissionService`：

| 身份 | 可见范围 |
|---|---|
| 超级管理员 / 系统角色 `project_manager` | 全部签到 |
| 项目负责人（`fire_user_company.role_type`∈{1,2,3} 或任务 `manager_id`） | 本人 + 负责项目下成员/任务干系人签到 |
| 普通员工 | 仅本人签到 |

负责人判定与项目成员以库表关联为准，不信任前端 `userId`/`companyId`，也不按手机号写死。

## 4. 设备管理

```text
GET 当前公司
→ POST /api/fire/equipment/list
→ 前端按 systemName 分组
→ 类型列表
→ GET /api/fire/equipment/detail/{equipmentId}
→ 新增或编辑
→ POST /api/common/upload
→ POST /api/fire/equipment/add|edit
→ 刷新设备列表
```

核心字段：`equipmentId`、`equipmentCode`、`companyId`、`buildingId`、`systemTypeId`、`systemName`、`equipmentName`、`location`、`expireDate`、`image`。

设备二维码扫描后把扫描值作为 `equipmentCode` 查询。如果二维码内容不是纯设备编码，原生重构时需要明确二维码格式协议。

## 5. 巡检登记

```text
GET 当前公司
→ POST /api/fire/inspection/myList
→ 新建巡检
→ 选择建筑、系统并录入设备状态
→ 上传照片
→ POST /api/fire/inspection/add
→ 后端写入当前 inspectorId/inspectorName
→ 返回 inspectionId
```

主要字段：`companyId`、`buildingId`、`inspectionType`、`systemType`、`equipmentName`、`equipmentCount`、`inspectionTime`、`equipmentStatus`、`imageUrls`。

## 6. 维保签到

```text
获取当前公司或由 taskId 反查任务
→ wx.getLocation 获取 GCJ-02 坐标
→ 获取公司任务列表
→ 选择签到/签退
→ 上传至少一张图片
→ POST /api/fire/checkIn/add
→ 后端计算与公司签到点距离并保存
```

关键字段：`companyId`、`taskId`、`checkInType`、`latitude`、`longitude`、`address`、`images`。

后端即使超出签到范围也会保存签到，并在响应中返回 `isInRange` 和 `distance`。是否允许范围外签到属于业务规则，需要产品或运维确认。

## 7. 故障报修

```text
选择当前公司、系统和可选设备
→ 上传故障图片
→ POST /api/fire/repair/add
→ 我上报的 / 派发给我的
→ 管理员或项目负责人 dispatch（必选处理人 repairUserId）
→ 未开工可 recall 撤回派发
→ 处理人 start（写入 start_time）
→ 处理人 complete（说明 + 图片）
```

状态：

- `0`：待处理（未派发，或撤回后恢复）。
- `1`：处理中（已派发；是否已开工看 `start_time`）。
- `2`：已完成。

关键字段：`repairUserId` / `repairPerson` / `dispatchBy` / `dispatchTime` / `startTime` / `completeTime`。

### PC 员工工作台（`maintenance_member`）

管理端 **消防管理 → 故障报修** 对员工展示工作台。页面为三张独立卡片（分类不在搜索表单内）：

1. **搜索卡片**：报修单号、单位名称、紧急程度、发现时间、搜索/重置。
2. **工单分类卡片**（`repair-category-card`）：待我处理 / 处理中 / 已完成 / 我上报的；`params[workbenchCategory]`。
3. **列表卡片**：工单表格（员工无新增/编辑/删除/导出工具栏）。

分类条件由后端结合当前登录用户生成，不接受前端传入任意 `userId`：

| 分类参数 | 条件 |
|---|---|
| `assignedPending` | `repair_user_id = 当前用户` 且 `repair_status = 1` 且 `start_time IS NULL` |
| `processing` | `repair_user_id = 当前用户` 且 `repair_status = 1` 且 `start_time IS NOT NULL` |
| `completed` | `repair_user_id = 当前用户` 且 `repair_status = 2` |
| `reported` | `reporter_id = 当前用户` |

列表请求：`POST /fire/repair/list`，表单字段 `params[workbenchCategory]`（白名单如上）。员工隐藏新增/编辑/删除/导出/派发/撤回；操作栏仅本人被派发工单显示「开始处理」「填写处理结果」。

### 处理权限

- **查看**：`canAccessRepair`（报修人、处理人、公司负责人、超管）。
- **开始/完成**：`canProcessRepair` / `assertCanProcessRepair`，必须 `repair_user_id = 当前用户` 且 `repair_status = 1`；完成前须已有 `start_time`。项目经理/超管不能冒用他人身份填写处理结果，需先派给自己。

### 接口

| 端 | 路径 | 说明 |
|---|---|---|
| PC | `POST /fire/repair/start/{repairId}` | 幂等写入 `start_time` |
| PC | `GET/POST /fire/repair/complete/{repairId}` | 仅更新说明/图片/完成时间与状态 |
| 小程序 | `POST /api/fire/repair/start/{repairId}` | 与 PC 同一 Service |
| 小程序 | `POST /api/fire/repair/complete` | 与 PC 同一 Service |
| 管理端 | `POST /fire/repair/recall` | 参数 `repairId`；权限 `fire:repair:accept` |

撤回：仅已派发、有处理人、尚未开始处理（无 `startTime` / 维修说明 / 图片）、未完成时可撤回；成功后清空处理人与派发信息，状态回 `0`。

### 角色权限（员工）

`maintenance_member` 应具备：`fire:repair:view`、`fire:repair:list`、`fire:repair:start`、`fire:repair:complete`；不应具备 `accept/edit/remove/export`（除非业务另行开放）。增量脚本：`backend/sql/upgrade_repair_employee_workbench.sql`。

### 紧急程度

当前枚举：`0` 一般、`1` 紧急、`2` 特急。新增/编辑接口校验 `UrgencyLevel.isValid`；列表非法历史值（如 `3`）显示「未知」，不直接暴露数字。历史数据迁移前需统计备份，见上述 SQL 文件注释。

## 8. 报告

```text
管理端：选择客户 → 选择该客户维保任务 → POST /fire/report/generate
→ 先落盘 DOCX 至 uploadPath/report/
→ 可选 LibreOffice 转 PDF（失败则保留 DOCX，整单仍成功）
→ 列表预览 GET /fire/report/view/{reportId}
   （前端 docx-preview 渲染 Word；库来源 https://github.com/VolodymyrBaydalka/docxjs）
→ 或下载 GET /fire/report/download/{reportId}

小程序：
POST /api/fire/report/list
→ GET /api/fire/report/detail/{reportId}
→ GET /api/fire/report/preview|download/{reportId}
```

- 管理端在线预览以 DOCX 为准；无 Word 文件时提示无法预览。
- `GET /fire/report/check/{reportId}` 返回是否可预览/下载及格式。
- 预览/下载使用相对路径与登录会话，不依赖写死的 `127.0.0.1` 或固定端口。
- 生产域名需配置为微信下载合法域名（小程序端）。


## 员工注册（部门二维码 / 邀请码）

```text
部门管理生成注册二维码（7 天）或发放邀请短码（唯一发码入口）
→ 员工打开 /register?inviteToken=... 或手工输入 inviteCode
→ 填写姓名 / 手机号 / 密码（无短信）→ 提交
→ 可信邀请自动通过 / 否则待审（可受限登录、不可派工）
→ 管理员在「用户管理 → 注册记录」通过 / 驳回（驳回无需填原因）→ 组员角色 + dispatchable
→ 派工后才有任务；空状态：暂时没有分配给您的维保任务
```

- PC 注册页视觉与登录页一致（居中卡片 `max-width:1000px`）；公司/部门由服务端解析邀请后只读展示。
- 注册码**唯一入口**：系统管理 → 部门管理 → 选中部门 → 生成 / 查看 / 停用 / 下载注册二维码；注册记录页不做发码。
- 注册记录：独立菜单页 `/system/user/registerRecord`，仅做待审列表与通过 / 驳回；用户列表 `/system/user` 只做正式用户与组织树筛选。
- 审核驳回无需填写原因（确认即可）；`audit_remark` 仍保留兼容历史与自动通过写入，列表不展示该字段。
- 审核状态仅约束自主注册来源（`register_source` ∈ qr / invite_code / direct）；历史用户与 admin 不受空 `audit_status` 误拦。
- 手机号唯一索引覆盖软删除用户；重复注册提示「该手机号已注册」。
- 有效邀请注册默认 `allow_admin_login=1` 且 `allow_mini_login=1`（可登 PC，仍非管理员）；自动通过时赋 `maintenance_member`。PC 登录校验不绕过。
