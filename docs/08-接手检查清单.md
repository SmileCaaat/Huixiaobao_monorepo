# 接手检查清单

## 1. 需要尽快确认的信息

### 生产服务器

- 服务器地址、SSH 端口和账号。
- `/opt/app/restart-ruoyi.sh` 的完整内容。
- 当前 Java 版本和 Java 可执行文件路径。
- 实际监听端口；代码默认 83，Docker 是 80，生产脚本尚不明确。
- JAR 实际名称和进程匹配方式。
- `nohup.out` 是否有日志轮转。
- 防火墙、安全组和磁盘告警方式。

### 数据库

- 生产 MySQL 地址、版本、数据库名。
- `DB_URL/DB_USER/DB_PASS` 由脚本、systemd、shell profile 还是其他平台注入。
- 最近一次备份和恢复演练时间。
- 完整 `fire_*` 表结构以及历史迁移顺序。
- 是否允许从生产导出仅结构的脱敏基线。

### 反向代理与域名

- `huixiaobao-admin.site` 的 DNS、证书和续期方式。
- Nginx/Caddy/云托管配置位置。
- `/profile/**`、报告下载和上传是否经过代理。
- 微信公众平台配置的 request/upload/download 合法域名。

### 文件

- 生产 `uploadPath` 实际绝对路径。
- 上传文件、合同附件和报告文件的备份策略。
- 维保报告统一存放在 `{ruoyi.profile}/report/`（默认 `./uploadPath/report/`），不再依赖 JAR 内 `classpath:static/report`。
- 管理端在线预览为 Word（docx-preview / [docxjs](https://github.com/VolodymyrBaydalka/docxjs)）；确认 `static/ajax/libs/docx-preview/` 已随 JAR 打包。
- 生成逻辑为 DOCX 先落盘，PDF 可选；无 LibreOffice 时应仍能生成并预览 Word。
- 若仍需要 PDF 产物：服务器是否安装 LibreOffice / 是否配置 `LIBREOFFICE_PATH`。

### 小程序

- 微信小程序管理员和开发者权限。
- AppID、主体、体验版和正式版发布权限。
- 是否还能找到原始 uni-app 工程；如果存在，需要与当前编译产物做差异比对。
- 线上用户当前最依赖哪些页面，哪些页面可以直接废弃。

## 2. 建议首周安排

### 第 1-2 天：环境可重复

- 在本地使用 JDK 21 完成 Maven 构建。
- 获取测试数据库结构，启动后端。
- 用接口工具验证登录、公司、任务、设备和上传。
- 在微信开发者工具导入当前小程序。

### 第 3-4 天：修 P0

- 修复 401。
- 修复分页和任务筛选。
- 确认 `updateMaintenance` / 消防维护统一入口可用。
- 新增正确的小程序首页统计接口。

### 第 5 天：建立基线

- 固化数据库 schema。
- 保存核心接口脱敏样例。
- 建立发布和回滚清单。
- 创建 `feature/native-rewrite` 并开始原生请求层。

## 3. 每次修改前

- 确认修改的是后端、当前编译小程序，还是未来原生分支。
- 搜索同一路径是否同时存在管理端 `/fire/**` 和小程序 `/api/fire/**` 实现。
- 核对 Java Domain、Mapper XML 和前端字段名。
- 确认是否需要数据库迁移。
- 不要在编译产物中扩大字段别名或复制请求封装。

## 4. 每次发布前

- 核对 [12-后端接口手册.md](12-后端接口手册.md) 与本轮改动的路径是否一致；小程序仅调用 `/api/**`。
- 小程序冒烟：登录 → 首页（`/api/fire/home`）→ Tab → 巡检测试列表/新增；工程内无 `common/vendor.js`、无 `@dcloudio`。
- Maven 构建成功。
- 数据库脚本经过测试环境执行。
- 旧 JAR 和数据库可回滚。
- 上传目录没有被打包或覆盖。
- 登录、公司切换、任务、设备、签到、报修、报告完成冒烟验证。
- 故障报修员工端：账号仅有 `fire:repair:view/list/start/complete` 时，PC 列表默认「待我处理」；开始处理后进入「处理中」；不能派发/编辑他人工单；小程序与 PC 状态一致。
- 故障报修员工端布局：搜索卡片与「工单分类」为上下两张独立卡片，分类不在搜索表单内。
- 维保任务列表：任务类型（全部/周期/临时）为搜索下方独立卡片；首页统计卡片快捷筛选仍可用；列表入口按钮为「消防维护」（无「（巡查测试）」后缀）；操作列两行：业务按钮一行，一键完成/编辑/删除一行。
- 维保检查项：外层三按钮改状态（选中无 √，仅颜色）；「其他说明」仅改备注与附件且不覆盖状态；三级「全部正常」只改空/`0`→`1`；二级类目「全部正常」排除测试与已保存项；PC 与小程序同一 `recordId` / 业务键。
- 情况简述：一级类目页「结论」→ `conclusion` 页；先执行 `upgrade_task_conclusion_fields.sql`；断言 `fire-task-conclusion.test.js` / `fire-task-category-all-normal.test.js`。
- 消防维护合并：先 `backup_inspection_test_records.sql` → `upgrade_merge_inspection_test.sql` → 发 JAR → 超管 `rebuildInspectionTestRecords`；回滚见 `rollback_merge_inspection_test.sql`。源码断言：`backend/tests/inspection-test-merge.test.js`。
- 维保类目统一：发支持“巡查/测试/保养”的新 JAR → 执行 `upgrade_maintenance_catalog_449.sql` → 确认 18 个一级类目及 `237 + 182 + 30 = 449` → 超管重建历史任务；源码断言：`backend/tests/maintenance-catalog-449.test.js`。
- 独立巡查测试：侧边栏菜单名为「巡查测试」；先 `upgrade_fire_inspection_module.sql` →（若仍显示巡检测试则）`fix_menu_inspection_to_patrol_test.sql` → `upgrade_fire_inspection_template_keys.sql` → 发 JAR；类目与消防维护模板一致；楼层 `-5F～-1F`/`1F～99F`；回滚 `rollback_fire_inspection_module.sql`；断言 `backend/tests/fire-inspection-module.test.js` / `maintenance-patrol-label.test.js`。
- 执行 `backend/sql/upgrade_repair_employee_workbench.sql` 后确认 `maintenance_member` 无 `fire:repair:accept/edit/remove/export`。
- 观察生产日志无异常后再结束发布窗口。
